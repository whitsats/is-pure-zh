# v7.1 修复说明：字库残影、标点过大、系统文本被截断

v7.1 不改文本内容，只修三处显示缺陷。三处都能独立复现、独立校验，下面是原因、
修法与校验值。

---

## 一、相关文件的格式（复现时会用到）

### ETC.AFS
带偏移表的归档：文件头 4 字节魔数 + 4 字节条目数，随后是条目表（每条 8 字节：
偏移、长度），表尾紧跟一段以 48 字节为一条的元数据（文件名在 +0，实际压缩长度在 +44）。

- 打进 ISO 时占 LBA 159082、槽位 17,889,280 字节。
- 字库是第 **4** 号条目 `FONT00.FOP`，压缩存放。

### FONT00.FOP
- 大小 1,200,128 字节，字形数据从 **0x5000** 开始。
- 每个字 288 字节 = 24×24 像素 × 4 bit，**但游戏每个字只用其中两位**：
  plane 0 用 bit0–1，plane 1 用 bit2–3（4 级灰度，游戏内都渲染成白色）。
- 字符位置换算（Shift-JIS 码位 → 槽位）：
  ```
  lead, trail = 码位两个字节
  row   = lead - 0x81            # 0x81–0x9F
  row   = lead - 0xE0 + 31       # 0xE0–0xFC
  index = row * 188 + (trail - 0x40 - (trail > 0x7F))
  slot, plane = divmod(index, 2)
  数据偏移 = 0x5000 + slot * 288
  ```
- 字宽/定位表在 `0x1e + index * 2`，两个字节分别是左边距与右边距。

### LZSS（游戏自己的变体）
- 头 4 字节是小端解压后长度。
- 4096 字节环缓冲，起点 `0xfee`；标志字节 8 位，1 = 字面量，0 = 匹配。
- 匹配编码 2 字节：`src = a | ((b & 0xf0) << 4)`，长度 `(b & 15) + 3`（即 3–18）。
- `制作粗圆修复字库.py` 里打包与解包两份实现都有，打包后会做一次往返校验。

### SLPM_665.70（主程序）
- 原盘 LBA 823692、大小 1,514,848 字节，与打到盘里的同长，可原地替换。
- 系统文本是**以 NUL 结尾的字符串**，内嵌控制符：
  - `%N` 换行/下一项；`%n` 选项之间的分隔；`%S` 选项文本位置；
  - `0x87 0x53` 是游戏自定义码位（不是合法 Shift-JIS），出现在选项行里。

## 二、字库残影（发糊）

**症状**：章节标题、菜单里未汉化的全角英文与数字（`１`、`Ｉ`、`I's`）重影、发糊。

**原因**：既然每个字只占两位，写新字形前必须把**这两位都清掉**。v7 的脚本只清了自己
那一位（`mask = bit`、`15 ^ bit`），另一位上残留的原版字形没被清掉，和新字形叠加。

- 对 v7 字库全量统计：v7 自己写过的汉字槽位是纯 level 1（两位都清过），所以中文看不出问题；
  只有 v7 没动过的全角英文/数字槽位（如 `8250 １`、`8268 Ｉ`）被覆盖后留下 level 2/3 的旧字形。

**修法**：`mask = 3`（plane 0）/ `mask = 12`（plane 1），两位一起清，再以 level 1 写入。
中文槽位的另一位本来就是空的，所以汉字字形与 v7 **逐像素一致**，不会因为这次修复变样。

---

## 三、标点过大

**原因**：v7 保留了原版约 24 像素满格的标点，比 20 像素的正文大一圈。

**修法**：把剧本实际用到的 25 个全角标点（`「」『』。，、？！…〜ー：；（）“‘”＆％－．`）
改用 18 像素方正粗圆。

**坑**：不能拿 Pillow 的 `textbbox` 给标点定位 —— CJK 字体下它返回的是**字宽框**而不是
墨迹框，`、`「`」` 这类窄标点会被摆偏。标点必须自己渲染到临时画布、取非零像素的
真实墨迹包围盒，再按字宽表摆放。

---

## 四、系统文本被截断（本次影响面最大的一处）

**症状**：
- 「从此处继续游戏吗？」这类确认框**只有问句，没有「是／否」**；
- 多行提示（存档中、记忆卡检查、免责声明）**只显示第一行**；
- 复制／粘贴／删除／写入 这类多项目菜单**只显示第一项**。

**原因**：v7 的文本替换工具写中文时，**按原日文行的字节长度逐行补 `0x00`**：

```
日文：ここからゲームを再開しますか？%N%Sはい%n◯／◯%n%Sいいえ
v7  ：从此处继续游戏吗？\0\0…\0%N%S是\0\0%n◯／◯%n%S否\0\0…
                        ↑ 这里出现内部 NUL，解释器到此为止
```

游戏的文本解释器按 NUL 结尾处理，读到第一个 NUL 就结束，所以 `%N` 之后的整行
（包括「是／否」选项）永远不会被渲染。v7 的 ELF 里共 **116 条**记录如此。

**修法**：以原版 ELF 为基准，逐条取出 NUL 分隔的记录；若汉化后的同一区间内部
出现 NUL（NUL 之后还有内容），就把该区间的 NUL 全部去掉后重新写回，尾部补零保持
记录总长度不变。控制符 `%N`/`%n`/`%S`/`0x8753` 的位置与原始日文完全一致，因此
行数与选项位置也与日版一致。

脚本会复核两件事，任一不满足就中止：
1. 合并后不能比原区间更长（中文比日文短，实际全部满足）；
2. 合并后的控制符骨架必须与原版完全一致 —— 这样能自动挑出「不是按行补零、
   而是被工具改了结构」的记录，避免误改。

`分析截断消息.py` 会把每条记录的中日原文、现状、修复后结果打印出来供人工核对。

---

## 五、复现步骤

材料：原版 ISO + Release 完整补丁包（含 `打盘/` 里的四个二进制）+
方正粗圆 TTF（需自备，仓库不附带字体）。

```bash
# 1) 文本：从原盘取原版 ELF 作基准，修 116 条被截断的记录
python 修复/系统文本/修复截断消息.py --原盘 game-original.iso \
      --v7elf 打盘/SLPM_665.70-patched.elf --输出 打盘/SLPM_665.70-fixed.elf

# 2) 字库：重写字形（清两位残留 + 标点 18 像素）
python 修复/字库/制作粗圆修复字库.py --字库源 打盘/FONT00-v6.FOP.bin \
      --字体 方正粗圆_GBK.ttf --输出目录 out

# 3) 把新字库压回 ETC.AFS
python 修复/字库/替换字库.py --afs 打盘/etc-v6.afs \
      --lzss out/FONT00-粗圆.lzss --输出 打盘/etc-v6-粗圆.afs

# 4) 出盘（BASE 默认 ~/workspace/is-pure/，game-original.iso 放那里）
cd 打盘
python3 build_v7.py etc-v6-粗圆.afs mac-v6.afs init-v5-lazy.bin \
        SLPM_665.70-fixed.elf game-v7.1.iso
```
