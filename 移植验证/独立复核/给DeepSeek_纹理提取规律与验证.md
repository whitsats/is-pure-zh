# 给 DeepSeek：素材提取规律与验证交接

日期：2026-11-13。目标是还原游戏素材以供原生移植研究；这份记录区分已经实测的结果和仍需验证的假设。

## 一、结论

角色立绘的主要拼接错误找到了一个可复用的修正：**按 32×32 小块跨 1024 像素存储行连续读取，而不是按完整部件宽度的条带在行末整体换行**。15 个试验条目中，多张原先重影、断裂的图恢复连贯；这些条目包括同姿势表情变体，不代表 15 个互相独立的构图，也不能证明全部立绘正确。

PCSX2 纹理转储实测并未让本次场景的素材自动变成完整图片：当前事件 CG 被转成多张 1024×32 长条，人物对话头像也被拆在长条里。它适合用于抽样核对，但逐场景收集素材效率低。**全身立绘是否也以碎片转储，尚未实测到，不能由这两例推断。**

## 二、CHR 人物立绘的候选规则

以下针对 `CHR.AFS` 中符合当前部件表结构的立绘条目，不是所有 CHR 条目、背景、事件 CG 或其他游戏的通用规则。

1. 本机原盘 `E:\Entertainment\IS\game-original.iso` 的 CHR.AFS 基址为十进制 `106958848`。`背景抽样验证\chr_body.py` 的 `entry()` 读取 AFS 表并调用 `移植验证\extract_bg.py` 的 `unpack()` 解压。原始研究发现条目常呈偶数像素数据、相邻奇数 TIM2 缩略图的配对；实际批处理需先识别条目类型，不能盲目套用。
2. 已测立绘像素区头长为 `0x100` 或 `0x180`，随后按 RGBA8888 解读。头部 `+0x80` 是小端 `u32` 部件数，`+0x90` 起是每条 8 字节记录：前四个 `u8` 分别为 `x/32, y/32, w/32, h/32`；`+4` 的小端 `u16` 含义仍未知；`+6` 的小端 `u16` 在已测非末记录可用于核对**已消费的累计 32×32 块数**，末项通常为 0。
3. 将解压后的像素区视作 `(-1, 1024, 4)`，32 像素高的一行包含 32 个 32×32 块。对部件表按记录顺序处理，每个部件内部按从上到下、从左到右的块顺序读取；所有部件共用连续块号 `tile`，不在部件边界清零。源坐标为 `sx=(tile % 32)*32`、`sy=(tile // 32)*32`，读完每块再 `tile += 1`；目标部件中的块坐标按 `y=0,32,...,h-32`、`x=0,32,...,w-32` 迭代。
4. 将部件放到表中 `(x,y)`。试验画布为 `704×480`；对已测样本，按非零 alpha 覆盖。部件重叠时的覆盖次序和 alpha 混合语义尚未充分验证。
5. 已测人物像素 alpha 最大值为 128，输出普通 PNG 时映射为 `min((alpha * 255 + 64) // 128, 255)`，先升为 `uint16` 防止溢出。旧版 `chr_body.py::save()` 把所有非零 alpha 设成 255，会丢失半透明边缘。

旧的“货架”假设在一个部件整条宽度放不进行尾时，直接把整条移到下一行，跳过了行尾仍可容纳的 32×32 块。它能让部分样本看似正常，也会让其他样本出现重复头部、断肢和缺块。**不要把 `chr_body.py` 开头关于货架模型已破解的文字当作最新结论。**

- 游戏中对话头像对应的转储长条：`E:\Entertainment\IS\PCSX2\textures\SLPM-66570\dumps\b85080bb405d1dc0-00001680.png`，可见头像被分段排列。

已复核：上述 CG 长条的首个 32×32 块 `dump[0:32, 0:32, RGB]` 与完整图 `EV_000[320:352, 128:160, RGB]` **逐字节一致**，最大/平均绝对差均为 0。这只证明一个 CG 块的 RGB 一致，并未逐像素验证整图、alpha 或 CHR 立绘。启动厂商标志的转储则可为完整 `640×448`；因此不同素材不能假设都以相同方式导出。

## 五、建议后续工作

优先以候选规则实现**独立输出目录**的批量立绘试验，不覆盖原始镜像、原提取图或现有研究文件。按头部识别目标条目，记录解压长度、部件表与累计块数、输入/画布边界、未消费块和 alpha 超范围；遇到异常要单列，避免静默截断。扩大不同人物、姿势和特殊条目的人工抽样，用缩略图筛查，再选少量场景与游戏运行画面核对。确认规则适用范围后再替换正式提取器。
