# CHR.AFS 统一批处理：废弃 chr_batch2.py 的"猜带宽"算法

日期：2026-11-13。承接《验证报告.md》《给GPT的技术摘要.md》《独立复核/给DeepSeek_纹理提取规律与验证.md》。

## 一句话结论

**全部 1473 个 CHR.AFS 条目（879 张全身立绘 + 594 张半身头像）共用同一套 `(x,y,w,h)` 部件表格式**，
用 `chr_body.py` 已验证的"全局块号"模型统一解析，**1473/1473 全部成功、0 失败**；
`chr_batch2.py` 对半身头像用的"穷举 15 种带宽、挑相关系数最高"算法是多余且劣质的旧分支，**已废弃**。

## 背景：此前的割裂状态

| | `chr_batch2.py`（旧） | `chr_body.py`（已验证） |
|---|---|---|
| 适用范围 | 全部 1473 条都用它跑，但只有半身头像那 594 条能跑出像样结果 | 只用于 879 条全身立绘 |
| 原理 | 猜：穷举 `WIDTHS = [128,144,150,160,...]` 15 种带宽，逐条带顺序平铺，挑与缩略图相关系数最高的 | 读：直接解析条目头 `+0x80` 的部件数 + `+0x90` 起每条 8 字节 `(x/32,y/32,w/32,h/32,flag,累计块数)` |
| 结果 | 1473 条里只有 594 条（40.3%）corr≥0.80"成功"，其余 879 条（全身类）corr<0.40 彻底失败——因为它们本质上需要"部件表+全局块号"而不是"单条带穷举" | 879 条：IoU 中位数 0.963，875/879 ≥0.80 |

**没人去验证过"那 594 条成功的半身头像，是不是其实也该用部件表模型"**——这是本次调查补上的缺口。

## 验证过程

1. 扫描全部 1473 个条目的配对缩略图尺寸，确认只有两类：`(160,112)` 879 条、`(35,33)` 594 条，无第三类。
2. 对 `(35,33)` 那 594 条，直接调用 `chr_body.py::build()`（不作任何修改）解析头部的部件表：
   - 发现它们的头部结构和全身立绘完全一致，只是 `count` 通常为 1（单个部件覆盖整个画布区域）；
   - 全量 594 条用同一个块号模型重建，与配对缩略图算剪影 IoU：
     ```
     594 / 594 可解析，0 失败
     中位数 0.9983　均值 0.9876　最差 0.8883
     IoU >= 0.95: 533/594　>= 0.90: 566/594　>= 0.85: 594/594（100%）
     ```
3. 目视核对最差的 10+10 条（全身类 + 半身类，见 `chr_unified/montage_worst_and_best.png`）：
   **全部干净，无重影、无错位、无断裂**。最差分数（0.798/0.888）全部来自缩略图构图差异
   （例如缩略图里混入另一个小尺寸剪影，或缩略图裁切范围与全身重建不同），不是解码错误——
   与《验证报告.md》6.5 节"IoU 只能当排序器"的既有结论一致。
4. 额外排除的两个"毛边"嫌疑（均不成立）：
   - **部件框重叠**：全量扫描 879 条全身类，0 条有部件边界框重叠；
   - **alpha 预乘**：用独立缩略图真值比对"直通 alpha"与"预乘解包"两种插值，预乘假设让颜色
     更接近真值的比例只有 0–40%（即更差），现有"直通 alpha、0–128 线性映射到 0–255"的处理是对的。

## 仍未解决、不阻塞当前结论的问题

- `+4` 这个恒为 2 的 u16 字段含义未知（怀疑与层/帧有关，但不影响静态重建）。
- 条目尾部中位 18 块（最大 31 块）的"未消费块"，表里没有坐标，含义未定，直接丢弃不绘制。
- 所有验证仍停留在离线重建 + 缩略图比对，**尚未与 PCSX2 实际渲染画面做逐像素核对**——
  这是下一步如果要对移植质量做最终背书时，唯一还没做但技术上可行的验证手段。

## 下一步建议

1. 把正式批量提取器切到 `chr_unified.py`/`chr_body.py` 的部件表模型，`chr_batch2.py` 及其产物
   （`chr_batch/` 目录下旧的穷举带宽结果、`chr_batch.csv`）标记为历史产物，不再作为素材来源。
2. 如需最终确认"游戏实际渲染画面也是这样"，挑 2-3 个已知编号在 PCSX2 里触发并开纹理转储，
   与 `chr_unified/` 的离线重建逐像素比对。
3. 背景（BG.AFS）与事件 CG（EV.AFS）的重建流程本身没有发现问题，不在本次修复范围内。
