# CHR.AFS 部件图集解码：现状与待评审问题

日期 2026-11-13。目标：从 PS2 游戏镜像里还原角色立绘（CHR.AFS），用于汉化工程的素材核对。
一句话结论：**布局规则大体正确（中位相似度 0.85，约 71% 目视正常），但有约 20% 的条目出现 32 px 级别的错位，
根因未定。**下面把所有已确认事实、已排除假设和待评审问题列清楚。

---

## 1. 容器与已知结构

- 镜像 `game-original.iso`，1,847,197,696 字节；`CHR.AFS` 偏移 **106,958,848**。
- AFS 内 **2946 项 = 1473 偶数项（像素数据） + 1473 奇数项（TIM2 缩略图）**，成对。
- 偶数项条目 = 头（`0x100` 或 `0x180`，判据 `(len-header)%8192==0`）+ **RGBA8888 像素流**。
- 头的关键字段：
  - `+0x80` u32：部件数量 count（1~40）
  - `+0x90` 起 count × 8 字节记录：
    - `+0` u8 `x/32`
    - `+1` u8 `y/32`
    - `+2` u8 `w/32`
    - `+3` u8 `h/32`
    - `+4` u16：除最后一条为 0 外，全部等于 2（**含义未定**，当前当作 flag 忽略）
    - `+6` u16 `B`：该部件结束位置，单位 = **1024 像素行**（最后一条为 0）
- 头部还有若干 12 字节小段，形如 `(0,0,640,448)`，判定为**显示帧**尺寸，非画布。

## 2. 画布

`704 × 480`，穷举统计得出：

- 879 个"部件图集"条目（配对缩略图为 160×112）中，`max(y+h)` **879/879 恰好 = 480**；
- `max(x+w)` 最大 = 704（12 条达到）；
- BG.AFS 的 `704×512` 来自固定解压长度 `0x160100`（`(0x160100-0x100)/4 = 704×512`），是整帧缓冲，
  **与 CHR 的精灵画布不是同一个东西**，不能混用。

## 3. 条带摆放（核心假设）

像素流按 **1024 px 行宽**切成 32 行高的"条带行"。宽度 w 的部件由若干 `32×w` 条带竖向拼成，
条带在同一行内从左到右连续摆放，游标 `x += w`，仅当 `x+w > 1024` 才换行、`x=0`，
**部件之间不重置游标**（"货架"模型）。

- w 整除 1024（32/64/128/256）时，这与"每行固定 1024/w 条"等价；
- 不整除（96/160/192）时才有差别，879 条里 **466 条**含此类宽度。

决定性证据：CHR 1386 前两件各 1 条（32 宽）→ 游标到 64；部件 2（96×448，14 条）从 x=64 铺到 1024（10 条）
再下一行 4 条，解出**完整的白衣少女立绘**；换成"每件另起一行"只得 0.144，"线性读"只得乱码。

## 4. 已做到的与量化的结果

- 1473 项全部可解析；879 个图集条目全部解码出图。
- 与配对缩略图做**剪影 IoU**（两边剔碎屑 <2% 主连通域、裁包围盒、归一化）：
  中位 **0.850**，均值 0.842；≥0.90 有 398，≥0.80 有 479，≥0.70 有 767，<0.70 有 112。
- **目视真值**（把 <0.80 的 400 条逐条渲染、逐格判读）：
  **170 条明确缺损 / 52 条边界 / 178 条正常**。
- 明确的"正确锚点"：CHR 6 (0.975)、0 (0.959)、4 (0.956)、1386 (0.947)、10 (0.925)、1914/2034/2154 (0.988)
  —— 与缩略图目视完全一致，无接缝。

## 5. 失败长什么样（用户反馈"肉眼可见有偏移"）

三类：

1. **整身重影**：画布上出现两个同一个人（双头/双身），一个正、一个偏 ~32–96 px。
2. **竖条铺开**：躯干被切成 32 px 宽的竖条，条与条之间左右/上下错开 32 px。
3. **白色缺口 / 块状遗骸**：人物身上有矩形透明洞，或旁边挂着矩形碎块。

典型条目：1272/1416/1488/1632/1344/1560（0.599）、1734…2334（0.618）、634/334/784（0.713，白色缺口）、
2416/2468/2800（0.63，灰块+洞）、1504（0.751，胸口白块）。

## 6. 已排除的假设（都有实测数据）

| 假设 | 结果 |
|---|---|
| 线性读（连续 32×w 块） | 乱码 |
| 每件另起一行 | 1386 掉到 0.144；1272 0.492；634 0.649 |
| 货架游标偏移 ±32/64/96/128 | 个别条目抬分（634 0.713→0.789）但好样本全崩（1386 0.947→0.70） |
| 每件起点按 w 或 64 对齐（留填充） | 全面下降 |
| 部件按 (y,x)/(x,y)/高度升/降序重排 | 均无普适提升 |
| z 序反转 / "先到先得"合成 | 剪影不变，视觉不变 |
| x 镜像、y 底对齐两种坐标约定 | 1272: 0.599 → 0.377 / 0.544，更差 |
| 宽度缩放 0.5/0.75/0.8/1.25/1.33/1.5/1.6/2 | 全部更差 |
| 旋转 90°/270° | 更差 |
| 条带高 4/8/16/32/64、行宽 1024/512/256/128 | 32/1024 最优 |
| 部件 0 是"其余部件的缩放预览" | 与缩放后的合成图相关性仅 0.33 / 0.24 / −0.02 |
| 只保留最大连通域 | 无改善（1272 0.599→0.682 但 1024 0.684→0.549） |

**结构校验（排除"解析漂移"）**：写了 5 项纯结构校验（count 与实读一致；`B` 严格递增且末条为 0；
由 `B` 差分算出的 h 为正且是 32 的倍数并与表内 h 一致；`sum(h*w)` 恰好等于像素流长度；
`x+w≤704`、`y+h≤480`）——**879/879 全部通过，0 违规**。
另逐字节比对 346 与 634（长度同为 655744）：**像素流 SHA1 不同**，是两张不同的图，各自表格自洽。

**自动检测器全部失败**（想让机器代替目视，均未成功）：

- 剪影自相关找"重复的一次"：好样本 767/767 也超阈值（人形自相似）；
- 部件接缝处的 RGB 跳变 / 全图基线：所有条目都在 1.1–1.4 倍，最高 2.04，无区分度；
- 内部长直边（块状遗骸特征）：坏 0–7、好 0–7，无区分度；
- 与缩略图逐像素 RGB 一致率：召回 86% 但误伤 143/178（**因为缩略图常是半身、图集是全身，构图不同**）；
- 轮廓内部透明洞占比：能抓白块，但也会抓"手臂与身体之间的自然缝隙"。

## 7. 关键的异常观察（最可疑的地方）

以 634 为例（13 件，`w=160` 的首件 `160×480 @ (288,0)`）：

- 首件本身就**是一张完整的人像**；
- 其余 12 件是 `32` 宽的竖切片，散布在 x=160…704、y=32…448；
- 这些部件在画布上**互不重叠（覆盖重叠率 0.0%）**；
- 但把它们全叠上去，就变成"同一个人画了两次"。

1272 同理：首件 `96×448 @ (320,32)` 已是完整小图，其余 8 件是竖切片。

也就是说：**同一人物似乎被存了两套表示（整张 + 竖切片），而条目里没有任何字段说明该用哪一套。**
`+4` 的 u16 目前全是 2（末条 0），是目前唯一还没解释的字段，怀疑与"层/帧"有关。

## 8. 待评审的问题

1. 在这种 PS2 精灵图集格式里，部件记录 `(x,y,w,h,B)` 的 `(x,y)` 是否可能**不是画布坐标**，
   而是相对于某个锚点/前一部件的偏移？（已测过 x 镜像与 y 底对齐，但没测过"相对上一件"的累加）
2. `+4` 的 u16（恒为 2）可能是什么？层号？帧号？调色板/混合模式？
3. "整张 + 竖切片"共存，是否意味着**部件表描述的不是一帧**，例如：切片属于不同动画帧，
   需要靠某个分组字段（`+4`?）才分得开？
4. 若上述都不成立，是否应该承认：**这些条目的正确渲染只能靠运行时抓帧确定**，
   解码器应当对低置信条目输出"已知不可靠"而不是硬拼？
