## 5. 容器头与透明区（两种幅面类型）

三个样本（12 / 20 / 278）的 256 字节头**完全相同**：

```
+0x00 u32 = 5            +0x04 = 128        +0x08 = 148      +0x0C = 256
+0x10 u32 = 256          +0x14 = 0x160100（= 解压总长）
+0x80 u32 = 1            +0x88 = 0x01C00280（高 448 << 16 | 宽 640）
+0x8C u32 = 2            +0x90 = 0x0F160000
```

- `0x01C00280` 与 ETC.AFS 内 TIM2 的宽高字段一致，即**显示画面 640×448**。
  但容器里实际画布是 704×512，二者不一致，说明显示阶段存在裁切或缩放，**仅凭容器无法确定**。
- alpha 只有 0 与 128 两级（×2 后为 0/255），是**硬边遮罩**；包围盒内部 100% 不透明。

两种幅面：

| 类型 | 内容矩形 | 缩略图对照方式 | 例 |
|---|---|---|---|
| 宽银幕背景 | (0,47) 起 684×298，占画布 56.55% | 缩略图取 `(0,11,160,81)` 的 160×70 带 | 20/40/80/120/160/200/240 |
| 满幅 CG / 提示卡 | (0,0) 起 684×478，占画布 90.71% | 缩略图用**整幅 160×112** | EV.AFS 全部、BG 278 |

684×298 = 2.295:1，684×478 = 1.431:1；对应缩略图 160×70 = 2.286:1、160×112 = 1.429:1，吻合到 0.4%。
游戏内最终贴图坐标仍需运行时截图确认，本轮未做。

## 6. 角色资源（CHR.AFS）：两类排布全部破解，1473 张图全部定位

`CHR.AFS` @ 106,958,848，2946 项 = 1473 张原始图 + 1473 张 TIM2 缩略图，全部可 LZSS 解压。

### 6.1 容器与像素格式（已确认）

- 自定义头长 0x100（826 项）或 0x180（647 项）；`u32[0]=0x0A`，`u32[1..9]` 为各段偏移，段间 12 字节。
- `+0x88` 的 `(高<<16|宽)` **不可靠**：1473 项中有 1392 项该字段为 (0,0)，
  只有少量条目给的是 640×448 或 140×130。不能当作图像尺寸使用。
- 像素为 **32bpp RGBA**，第 4 字节是 alpha（取值 0–128，与 BG 同样需要 ×2）。
- 所有条目的像素数据都是 8192 字节（64×32 页）的整数倍，`raw_len` 范围 131328–786816。

### 6.2 排布规则（已确认）

1. 像素流按 **1024 像素行宽**读取（= 16 个 64×32 页并排），得到一条条 1024×32 的“条带”。
   判据：alpha 的垂直差在 1024 行宽下为 0.61，其他行宽为 12.7–65.1；全身类为 1.69–1.98 对 14+。
2. 每条条带内，图像被切成 **32 行高的横带**，按固定步距左右并排。
3. 把所有横带自上而下堆叠即得原图。

CHR 2 的直接证据：1024×32 条带里 alpha 的占用列恰好是
`[(0,150),(160,150),(320,150),(480,150),(640,150)]` —— 宽 150、步距 160、共 5 带，
堆叠后为 160 宽、5×32=160 高的图像，内容是完整人物半身像。

带宽用配对缩略图作判据扫描（`chr_width_oracle.py`）：160 → corr **0.885**，次优 152/384 只有 0.35/0.33。

### 6.3 全量批量结果（1473 对）

|---|---|
| 参与评分的配对 | 1473 / 1473 |
| corr ≥ 0.99 | 14 |
| corr ≥ 0.95 | 384 |
| corr ≥ 0.90 | 547 |
| **corr ≥ 0.80** | **594（40.3%）** |

分布有**明确断层**：594 张在 0.80 以上，其余 879 张全部低于 0.40，没有中间地带。
成功的 594 张特征完全一致：

- 缩略图都是 35×33；失败的全是 160×112。
- 最优带宽**一律是 160**，画布 160×160，立绘包围盒 150×140。
- 最佳样本 CHR 2888：corr **0.995**，平均 RGB 差 **4.4**（与背景验证的 1.6–5.3 同量级）。

### 6.4 全身类条目（160×112 缩略图）：部件图集格式已破解

剩下的一类（879 个条目）不是单幅图，而是**按坐标摆放的部件图集**，头部 12 字节小段**不是**坐标表，
真正的部件表在 `+0x80`：

```
+0x80  u32         部件数量 count
+0x90  count × 8B  部件记录，每条：
        +0  u8     x / 32
        +1  u8     y / 32
        +2  u8     w / 32
        +3  u8     h / 32
        +4  u16    =2（末条为 0）
        +6  u16    该部件**结束**处的累计行偏移（行 = 1024 px，末条为 0）
```

**逐条验证（CHR 10，10 个部件，实测宽高与记录完全一致）**

| # | x | y | w | h | 实测解码尺寸 |
|---|---|---|---|---|---|
| 0 | 256 | 0 | 128 | 480 | 128×480 ✓ |
| 1 | 544 | 0 | 32 | 32 | 32×32 ✓ |
| 2 | 224 | 32 | 32 | 448 | 32×448 ✓ |
| 3 | 384 | 32 | 64 | 448 | 64×448 ✓ |
| 4 | 192 | 64 | 32 | 160 | 32×160 ✓ |
| 5 | 448 | 128 | 32 | 352 | 32×352 ✓ |
| 6 | 480 | 224 | 32 | 256 | 32×256 ✓ |
| 7 | 192 | 288 | 32 | 192 | 32×192 ✓ |
| 8 | 512 | 288 | 32 | 32 | 32×32 ✓ |
| 9 | 160 | 448 | 32 | 32 | 32×32（末条）✓ |

**摆放规则（块号模型，2026-11-13 修正）**：像素流按 **1024 px 宽 × 32 行高** 的「存储行」存放，
每个存储行 = **32 个 32×32 块**。解码时所有部件共用一条**连续块号 `tile`**，**不在部件边界清零**：

```
sx = (tile % 32) * 32      sy = (tile // 32) * 32      # 源块在存储行里的位置
部件内按 y = 0,32,…,h-32、x = 0,32,…,w-32 的顺序逐块取回，拼成 w×h，再按 (x,y) 贴到画布
tile += 1 每取一块；跨部件继续递增
```

- `w ∈ {32,64,128,256}` 时，它与旧「一条宽 w 的条带整行换行」模型等价，所以早期版本看不出区别；
- `w ∈ {96,160,192}` 时两者不同：旧模型在行末放不下整条就换行，**跳过了行尾仍可用的块**。
  全量对比：**中位 IoU 0.850 → 0.963，<0.70 从 112 条降到 0 条，477 条变好、0 条变差**。
- 高度一律**以表里的 h 为准**（早期版本对末件用 `(total−pos)/w` 反推，会多读十几个块）。
  按表解码后，**843 / 879 条仍有未消费块**：中位 18 块、最大 31 块、合计 14133 块（1 块 = 32×32 = 1024 px），
  说明条目尾部还有表未描述的像素；这些块不参与绘制，`chr_body.csv` 的 `leftover_tiles` 列逐条记录。
- alpha 实测最大值只有 **128**（7 位），输出 PNG 需 ×255/128，否则半透明边缘会被压成全不透明。

验证：CHR 634（`w=160`）按旧模型是 0.713 且胸口有白块，按块号模型是 **0.981** 且完整；
CHR 1272 `0.599 → 0.956`、CHR 346 `0.678 → 0.976`；原本就对的 CHR 6/1386/0/4 数值不变。

**画布：704×480**（多次核实的结论）。证据是穷举的，不是抽样：

- 全部 **879 / 879** 个全身类条目，`max(y + h)` **无一例外等于 480**；
- `max(x + w)` 的最大值为 **704**（12 个条目正好顶到 704，其余按角色宽度在 448–608 之间）。

它和 BG.AFS 的 **704×512 不是同一个东西，不应当混用**：

| | BG.AFS | CHR.AFS |
|---|---|---|
| 解压长度 | 固定 `0x160100` | 随条目变化（131328–786816） |
| 画布来源 | 由缓冲区长度反推：`(0x160100−0x100)/4 = 704×512` | 无固定缓冲区，只能由部件坐标得出 `max = 704×480` |
| 性质 | 整帧背景缓冲（四周留白） | 角色精灵画布（脚底统一贴 y=480） |

宽度两者都是 704（游戏内部帧宽），高度不同是因为一个是整帧缓冲、一个是精灵画布。
头部 12 字节段的 `640×448` 是**显示帧**尺寸，两者都不是它：704−640 = 64、480−448 = 32。

**为什么之前全部失败**：早期把每个条目当成「单幅图 + 横带重排」，而实际是「N 个部件各自重排再按坐标叠加」，
两者在部件数为 1 时（= 前半节的 594 张半身像）恰好等价，所以那一批能成功；全身类当时全部 corr < 0.40，
其中 `w` 不整除 1024 的那部分又在之后用「每行固定 1024/w 条」的简化模型重现了一遍错误，
后来换成“货架游标”（行末放不下就换行）只修好了一半，直到改成**全局块号**模型才完全消失。

### 6.6 结构校验与目视复核

**（1）部件表不会漂移（先排掉解析问题）**。`chr_check.py validate` 对格式做了 5 项纯结构校验，
不涉及任何摆放假设：C1 count 与实读记录数一致且不越界；C2 末条 `B=0`、其余严格递增；
C3 由 `B` 差分算出的 `h` 为正且为 32 的倍数，并与表内 h 一致；C4 由 `B` 差分累计出的长度恰好等于
像素流长度（即 `B` 字段自洽）；C5 `x+w ≤ 704`、`y+h ≤ 480`。

> **879 / 879 条全部通过，0 项违规。**

但 **C4 管的是 `B` 字段，不管表内 h**：按表内 h 解码后，**843 / 879 条**会在末尾留下未消费块

### 6.8 下巴/颈部“固定 y 错位”排查（已定位：源画锯齿+引擎滤波，非解码错位）

用户反馈人物下巴处有一条固定 y 的横向错位。以 CHR 6 / 2778 / 2850 / 1506 为典型条目做了四组检验，
并把 `y=140–200` 带放大 3 倍与缩略图并排比对（`chr_body/chin_{编号}.png`，
上=重建、中=缩略图、下=部件分色）：

| 检验 | 方法 | 结果 |
|---|---|---|
| 结构：下巴在不在部件边界上 | 4 条的部件表 | **不在**。人物按**竖列**存储，下巴总落在中央列 P0（`y=0/32`，`h=448/480`）内部；`y=160` 等边界只出现在肩部外侧列 |
| 相邻件纵向对不对齐 | 共享竖边的 RGB 不连续度，dy∈±96 步 32 | 4 条全部 **dy=0 最优**（代价 3.1–66，多数 <16）；dy=±32 时升到 24–89，多数为 3–6 倍 → 没有一件被上下放错 |
| 全量：部件会不会互相遮挡/切掉一条 | `chr_yscan.py` 扫 879 条 | 跳部件重叠 **0 条**；剪影内部被切掉横带 **0 条** |
| 与缩略图的竖直对齐 | 轮廓余弦，搜 dx/dy | 最佳 dx≈−11、**dy≈0（±2）**，上下半身结论一致 → 竖直位置与缩略图一致 |

边界行跳变比邻域中位数 ≥3 的有 298 条，但抽查最高的两条都是**画稿本身的强横边**，不是接缝：
CHR 396 `y=352`（粉上衣→深色裙腰）、CHR 1752 `y=416`（过膝袜口），见 `chr_body/edge_396.png`、
`chr_body/edge_1752.png`。这也再次说明“行跳变”不能当接缝判据。

**结论（2026-11-13 复核）**：在上述 4 条及全量 879 条里**没有再现 tile/部件错位**；半身头像（含 2792/2840）的台阶已进一步定位——

1. **PCSX2 纹理转储逐像素核对**（工具：`chr_dump_compare.py`）：把 1024×32 转储与条目的虚拟行（像素流前 32×1024）比较。CHR 518 与转储 `b85080bb405d1dc0-00001680.png` 的 **RGB 与 alpha 均逐像素完全一致（max diff 0）**——这只证明“虚拟行格式与引擎纹理一致”，**不等于核对了 518 的解码，更不等于核对了 2840**。2840 本人**未被转储**，且经人工长时间推进（转储累计 389 个，50 张 1024×32）后 2792/2840/2894/2912/2768 **均无匹配**（`chr_dump_compare.py` 全部 `NOT DUMPED`）——实机画面里人物用的是站立全身像（body 精灵），带底色的半身像纹理没有被上传，所以半身像的 PCSX2 转储核对**靠实机推进拿不到**。2840 的解码结论目前靠缩略图真值 + 518 的格式验证。结果：`chr_unified/dump_compare_result.csv`。
2. **双线性复现**：`chr_bilinear_composite.py` 把同一精灵用双线性放大（4x）后，下颌/耳边台阶被磨平，与第一张（游戏渲染）的平滑观感一致；最近邻放大则保留生硬锯齿（`chr_unified/_bilinear_2840.png` vs `_nearest_2840.png`）。

即：台阶是**源画对角线在 1:1 原生分辨率下的锯齿**，在最近邻放大下暴露；游戏以双线性放大并合成到场景背景，锯齿被滤波掩盖。解码器（块号模型）无需改动；若要复现游戏观感，用双线性合成脚本，不要用最近邻。

## 8. 音频（VOICE.AFS / SE.AFS）：可导出并播放

两者条目都是 **CRI ADX**，非 LZSS。头为大端：

```
0x00 0x8000 | 0x02 版权串偏移(0x24) | 0x04 编码 3(4bit ADPCM) | 0x05 帧长 18
0x06 位深 4 | 0x07 声道 | 0x08 采样率 | 0x0C 采样数 | 0x10 高通 500 | 0x12 版本 4
数据起点 = 版权串偏移 + 4 = 0x28，每帧 = 2 字节 scale/filter + 16 字节 = 32 采样
```

| 条目 | 声道/采样率 | 时长 | 帧数 | filter 集合 | 峰值 | RMS |
|---|---|---|---|---|---|---|
| VOICE 0 | 1ch / 48000 | 2.65 s（头声明 127236 采样） | 3978 | {0, 8} | 10710 | 801 |
| VOICE 100 | 1ch / 48000 | 1.99 s（95287） | 2979 | {0, 8} | 1022 | 111 |

正确性的间接证据：帧边界跳变均值 473 与帧内均值 463 基本相同；无样本超过 16000；开头为静音。

**限制**：文件头的系数区全为 0，本轮按“无预测（coef=0）”解码，输出为 `nibble × scale`。
若运行库另带默认系数表，音色会有差异；**本轮没有实际试听**，只做波形连续性检查。
